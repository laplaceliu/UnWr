## 一句话定位

**UnWr（Unlimited Writing）**：跑在 DeepSeek Harness 上的小说写作 AI 智能体——你说一句"帮我写一部玄幻网文"，一个 AI 编辑部替你从设定、大纲写到成稿，所有数据落在你自己的飞书账号里。

**一句话记忆点**：不是"AI 帮你续写一段"，而是"一家 AI 出版社"；不是一次性上下文，而是**记得住 500 章前埋的伏笔**。

## 一、面向写作者的卖点

### 1. 一个 AI 编辑部：主编排官 + 7 个领域子代理

- **世界官 / 人物官 / 大纲官 / 起草官 / 改稿官 / 评审官 / 卡文救援官**，各自有独立职责与专属工具集
- **角色即权限（硬约束）**：评审官的工具白名单里**没有任何写工具**——它永远不可能替你改稿，只诊断不代笔；救援官只产出候选分支方案，不写正文
- 四种工作模式 = 角色组合 + 权限开关：协作助手 / 全自动生成 / 教练评审 / 协作+自动，随写随切
- 用户全程说人话，不用记任何工具名或命令

### 2. 分层记忆（L0–L4）：治好 AI 长篇失忆

- 五层记忆模型：近 3 章**完整原文**（保语气、保细节）→ 近 12 章**摘要+事件索引** → **卷级摘要** → **全书层**（全书摘要+人物最新状态+未回收伏笔+主线进度，每次必注入）→ 全文**按需回溯**（关键词定位到块）
- 核心价值：**上下文成本 O(1) 而非 O(章节数)**——写第 300 章时的记忆注入体量与写第 10 章相同（约 20k token），长篇连载不撑爆上下文
- 每章写完自动沉淀记忆：结构化章节摘要（固定模板，可机器比对）、事件索引、人物状态快照（位置/伤势/情绪/持有物/关系变化）

### 3. 一致性检查体系（16 项）：伏笔、时间线、人设全盯着

- 规则型免模型：伏笔超期未回收告警、时间线倒序检测、**人物分身检查**（同一时刻出现在两地）、伤势跳变、道具凭空出现/消失、称谓混用（别名全文检索）
- 语义型模型判定：设定冲突（正文 vs 词条）、人设崩坏四子项（性格违背/口癖错用/动机不合理/**知识越界**——人物说出不该知道的事）
- 题材专项：推理向的**线索公平性**（揭晓时读者必须能回想起线索）、纯文学的**意象母题复现**
- 每条问题落库到"检查问题表"，带 **block_id 精确定位**到段落，可标已忽略（兼作负反馈）

### 4. 三套题材预设：一套系统，三种笔感

- **中文网文 / 类型小说 / 纯文学**三套预设，30+ 个参数维度（章节字数、爽点密度、章末钩子强度、设定自洽严格度、线索公平性、意象密度、心理描写深度、视角限制……）
- 设计巧思"统一维度，差异化取值"：网文的"爽点"、推理的"张力点"、纯文学的"情感强度点"在系统里是**同一个维度**——新增题材（历史正剧/轻小说）只需一组参数值，零代码
- 一句话概括三套预设：网文快、爽、勾人；类型小说严、密、公平；纯文学慢、厚、有余韵

### 5. 内容红线系统：14 条红线，三档分级，防误杀

- 严禁 / 高危 / 审慎三档，每条都给**合规改写方向**（如：军警法不做系统性反派 → 可以有坏个体，但必须有同系统正面力量纠正）
- **防过杀是显式设计**：每条红线都带"不属于本条"的反例清单——写鬼怪 ≠ 宣扬迷信，玄幻的神魔体系不会被误判宗教宣扬；"呈现黑帮的荒诞 ≠ 美化黑道"
- 严重度由档位裁决、不采信模型自报；三档严重度与题材阈值的数学关系（严禁恒阻断、审慎恒不阻断）由单元测试的不变量断言守卫
- 红线跨题材恒定，不进题材预设参数——防止切题材时红线"漂移"

### 6. 你的数据在你手里：飞书即出版社

- **13 张多维表格 + 云文档正文**，全部存在用户自己的飞书账号，不是厂商的服务器
- 结构化数据直接可视化操作：章节进度**看板视图**、公式字段自动算**累计字数/完成率**、伏笔表带公式自动展开埋设章节标题、人物 ↔ 章节**双向关联自动反向填充**（写章时登记出场人物，人物表的"出场章节"自动长出来）
- 作品 → 卷 → 章**四级知识库目录树**，飞书原生版本历史、评论批注全可用
- 换工具不锁死：全部数据随时 `record-list --format ndjson` 导出

### 7. 改稿是外科手术，不是推倒重来

- 句级 `str_replace` / 段落级 `block_replace` / **块区间一次替换**（跨多段一次完成），先预检后动手——跨段落 match 在任何 I/O 之前被拦截，给出三条出路而不是失败重试
- 改稿留痕：每次编辑进飞书原生版本历史，可回滚可对比
- 改稿后**记忆自动标陈旧**，下次起草自动重对齐——改稿不丢记忆

### 8. 卡文救援官

- "第 12 章我不知道怎么写" → 基于人物状态、未回收伏笔、大纲约束生成 3–5 条候选分支（悬疑向/情感向/反转向），每条含场景梗概、钩子设计、伏笔调用、字数预估
- 候选分支落库存档，未采用的留档复用

## 二、面向开发者 / 技术受众的卖点

### 9. 意图级工具：28 个工具封装 200+ 条底层命令

- 工具按**智能体意图**定义而非 CLI 命令镜像：`novel_write_chapter(章节号, 正文, cast)` 一次搞定建文档 + 建索引 + 建目录节点 + cast 登记；`novel_build_context(章节号)` 内部并发拉取五层记忆
- 三层架构：Tool 层 → 领域服务层（纯 TS 可 mock）→ 飞书适配层。lark-cli 的所有参数陷阱（`@file` 仅相对路径、长 JSON 禁内联、Markdown 转义、block_id 失效…）**终结在适配层**，上层代码永远不知道 CLI 的存在
- 未来换飞书 Node SDK 只动适配层，领域层与工具层零改动

### 10. 基于实测数据的架构决策（不是拍脑袋）

- 实测 lark-cli 单次调用 640ms 中**进程开销仅占 10%** → 推翻"为性能必须用 Node SDK"的直觉，决策 shell out
- 实测并行加速比 **3.8×（近线性）** → 性能解法是上下文组装器 + 并行 + 缓存，起草一章 11 次调用从串行 7s 降到 2s
- 需求阶段 **40 项飞书能力逐项实机验证**，验证矩阵 + 踩坑清单成文（docs/requirements/01）

### 11. 可靠性工程：为"分布式数据一致性"写了个自愈层

- link 回填**写后读回验证 + 退避重试**：飞书平台对新建记录的批量关联写入存在静默丢失（实测 60% 失败率、全程零报错），UnWr 用"写→读回→不过就重试"防御，实测一次重试后 100% 存活
- 写后列表索引延迟 ~6s：用进程内写缓存绕开，"写后立即查"永不扑空
- **重名字段自愈**：早期版本可能产生重名字段导致数据静默丢一边，`repairDuplicateFields` 幂等修复——改名隔离 → 按 field_id 对位读原始数据 → 并集回填 → 读回验证通过才删多余列，失败/中断安全可重入
- 会话默认作品**跨进程持久化**（仓库外 `~/.unwr/work-state.json`）：DSH 重启后零调用恢复上下文；本地作品注册表与云端搜索结果合并——飞书新建库有分钟级搜索索引延迟，本地注册表兜底

### 12. 安全默认值

- **不暴露任何删除类操作**：table-delete / record-delete / 覆盖写一律不注册给模型——一次幻觉不会删库
- **隐私红线**：仓库与 git 历史中无任何个人路径、真实 token（曾用 git filter-repo 全量清理并强推）；工作状态落盘在仓库外

### 13. 质量保障金字塔

- **39 个测试文件、300+ 单测**：schema 不变量、注册表一致性（persona 里提到的工具必须真实存在）、工具 schema 契约（含"action 含 query 则 required 必须恰好是 ['action']"这类真实踩坑回归）
- **工具体检 harness**（`pnpm test:tools`）：对全新库按真实编排时序打 38 发探针，覆盖全部 28 个工具，逐项报告
- **端到端 agent e2e**（`pnpm test:agent`）：headless 无人值守跑完整"建作品→写章→沉淀记忆→评审"全流程（实测 564s 成书），验收脚本直接落库校验数据
- 落库验收优先于报告验收：智能体"说自己做了"不算数，数据真的落库才算

### 14. Web 工作台

- `dsh web` 启动后浏览器打开 `/workbench`，无需命令行即可使用

## 五、建议的宣传侧重（个人判断，供参考）

1. **主推"编辑部"叙事**（多智能体 + 角色即权限）——差异化最强，一句话讲得清，且有"评审官不能写稿"这种天然的故事点
2. **次推"长篇不失忆"**——直接命中所有用过 AI 写长文用户的痛点，O(1) 上下文是可量化卖点
3. **飞书数据主权**对飞书存量用户转化率高，且"看板/公式/双向关联"截图即可展示
4. 工程向卖点（自愈层、验证矩阵）适合发技术社区（掘金/V2EX/HN），与产品向宣传分渠道投放
