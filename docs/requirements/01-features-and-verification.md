## 三、硬约束与踩坑清单（已实测，开发期必须遵守）

### 3.1 参数传递

1. **`@file` 只接受相对路径**。传 `/tmp/x.json` 报 `unsafe file path`。必须先 `cd` 到目标目录再用 `@filename`。
2. **`--json` 不支持 stdin**（`-` 会报 JSON 解析错误）。仅 `--content` / `--pattern` 支持 `-`。
3. **长 JSON 禁止内联**。伏笔表字段 schema 内联传参直接失败；改 `--fields @file` 后成功。复杂/长 JSON 一律走文件。
4. **shell 单引号里 `\n` 是字面量，不是换行**。章节正文必须用文件（`--content @file`）、heredoc 或 stdin 传入，否则整章变成一行，且 `#` 标题无法转成标题块（outline 为空）。
5. 多行内容优先 `--content @./file.md`；字面量以 `@` 开头时用 `@@` 转义。

### 3.2 命令格式

6. **`record-batch-update` 的 `update_records` 是 map 不是 array**：`{"update_records":{"recA":{...},"recB":{...}}}`。传数组报 `Expected object, received array`。
7. **`record-batch-create` 的 `create_records` 是 array**：`{"create_records":[{...}]}`。与 update 不对称，注意区分。
8. **`--json` 后不能直接跟 `--jq`**（会被当作位置参数）。用 `--format json --jq '...'`。
9. **`--jq` 与 `--format markdown` 互斥**。
10. `formula` / `lookup` 字段创建必须带 `--i-have-read-guide`；`field-update` 属 high-risk，需 `--yes`。

### 3.3 数据建模

11. **优先用 `formula`，不要用 `lookup`**。官方指南明确：Formula 是 Lookup 的严格超集，跨表引用与聚合一律用 Formula。
12. **批量上限**：写入 200 条/批；ndjson 导出默认 2000 条/次。
13. **文本字段容量**：实测 8400 字符无截断，足以承载章节摘要与设定正文。更长内容（如完整章节正文）应放云文档。
14. **`link` 双向关联会自动在对侧表生成反向字段**，反向值自动填充，无需手工维护。
15. **`drive +sync` 只同步 `type=file`**，云文档（docx/sheet/bitable/mindnote/slides）与快捷方式全部跳过——这直接决定正文存储选型（见开放问题 Q1）。
16. 创建 Base 时不带 `--fields` 会生成平台默认的「数据表」，需显式删除或改用作作品元信息表。

### 3.4 正文写入

17. **Markdown 特殊字符需转义**：`\`、`*`、`_`、`[]`、`$`、`~`、`<` 无条件转义；`#`（行首）、`+`（行首）、`-`（行首）、`>`（行首）位置敏感转义。
18. **`docs +fetch` 导出的内容已带转义，不要反转义**，否则回写时字符会被 Markdown 语法吞掉。
19. **`str_replace` 的 `--pattern` 必须使用转义后的形式**才能正确匹配。
20. `block_replace` 前先 `docs +fetch --detail with-ids` 拿最新 block id；结构变更后 block id 会变，需重新获取。
21. `str_replace` 不支持资源（图片/附件）替换，多块替换用 `block_replace`。

## 四、待确认的开放问题

| # | 问题 | 为何关键 | 建议倾向 |
|---|------|----------|----------|
| **Q1** ✅ | 章节正文用**云文档（docx）**还是**原生 Markdown 文件**？ | 云文档：富文本、原生版本历史、评论批注、`keyword` 块级检索（已验证）；Markdown：可 `diff` 精确到行、可被 `drive +sync` 双向同步、纯文本易流转。**二者不能兼得**（sync 跳过 docx） | **已决策：云文档（docx）**。Markdown 仅作导出/备份格式（见下） |
| **Q2** ✅ | Web 应用是**直连飞书 API** 还是**本地缓存 + 同步**？ | 直连：数据单一真源，但离线不可用、有 API 频率限制；缓存：响应快可离线，但需解决冲突 | **已决策：本地缓存 + 按需同步**，飞书为 source of truth |
| **Q3** ✅ | 一个知识空间对应**一部作品**还是**多部作品**？ | 决定目录树层级：空间→作品→卷→章 vs 空间→卷→章 | **已决策：一个空间多部作品**（四级结构：空间→作品→卷→章） |
| **Q4** ✅ | 章节正文粒度：**一章一文档** 还是 **一卷一文档**？ | 一章一文档：块 id 定位精确、版本粒度细、便于单章生成；一卷一文档：上下文连续 | **已决策：一章一文档** |

### Q1 决策的连带影响（重要）

选 docx 意味着**放弃 `drive +sync`**（已验证：sync 跳过所有云文档）。连带结论：

- 章节正文同步必须走 `docs +fetch` / `docs +update`，不能依赖目录级同步
- 「AI 改了哪些字」的可审阅性走 `docs +history-list` + 版本对比，而非 `markdown +diff`
- 若后续确实需要精确到行的 diff，方案是：**导出为 Markdown 副本后 diff**（`drive +export` → `markdown +diff`），作为辅助审阅手段，而非主存储
- N3「本地目录同步」功能降级：仅能同步 Drive 文件夹中的素材/导出物（type=file），**不能同步章节正文**
| **Q5** | 是否复用飞书文档原生版本历史做多版本管理？ | 原生历史免费但粒度为"每次编辑"，无语义标签（如"AI 初稿/人工修订"） | 倾向 **复用原生历史 + 自定义语义标签字段** |
| **Q6** | 智能体运行日志与对话记录存在哪里？ | 飞书表/文档/本地 三选一 | 待定，倾向本地（高频写入） |
| **Q7** | 是否需要多人协作（编辑共享作品）？ | 影响权限模型设计 | 待定，首版假设单人 |
